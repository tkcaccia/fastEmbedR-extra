# fastEmbedR implementation and benchmark goals

Agreed with Stefano on 5 November 2026. The Implementation Brief is the controlling protocol. This document makes the release and execution gates explicit; it does not relabel development pilots as publication results.

## 1 Required implementation matrix

The four user-facing analysis calls are `pca()`, `tsne()`, `umap()`, and `graph_cluster()`. The required algorithms are PCA; 2D and 3D t-SNE; 2D and 3D UMAP; Leiden; and Louvain. PCA is checked at ranks 2, 3 and 50 where admissible. For each method, test both all-row fitting and landmark fitting with all-row output, and both resident and file-backed input/state routes as distinct cases. The backend axis is single CPU, multicore CPU, single Metal GPU, single CUDA GPU, and coordinated multiple CUDA GPUs. Multi-GPU Metal is excluded because the available Mac has one GPU. The 140-row interim table is `benchmarks/capability-matrix-20261105.csv`; its status meanings are documented beside it. A route is complete only after a real-device test, output and quality checks, memory accounting, and explicit no-fallback metadata. A failed or unsupported route remains visible until fixed; it is not silently dropped from the manifest.

Formal file-backed performance comparison runs on Silvano's Mac for CPU and Metal. File-backed CUDA development and correctness run on Chiamaka when idle or on Hugging Face with non-Deep1B data; they do not become HPC results. UCT HPC scientific work is resident only, on CPU and allocated L40S devices. Metal is single GPU, while CUDA multi-GPU tests one coordinated fit on each requested device set. Deep1B is restricted to Mac and HPC fastEmbedR stress tests.

## 2 Benchmark code control

Before admitting a case, the planner and worker independently verify the method, dataset identity, exact source-row selection, storage mode, fit scope, expected rows, output dimension/rank, parameter profile, physical CPU/GPU allocation, backend route, and spill policy. The worker fails before calculation if an HPC path resolves to file-backed or streamed scientific state. Every L40S allocation or array element contains exactly one case, seed and repetition. Test this rule with deliberate rejected manifests and lifecycle failure fixtures.

Each result records package/benchmark commit, immutable image/build and dataset identity, machine and GPU UUIDs, requested and effective workers, input conversion, search, fit and output times, quality, peak RSS/VRAM, file-backed I/O where permitted, scheduler outcome and cleanup. Large image digests are computed only in allocated compute jobs and reused through immutable manifests; the HPC head node performs lightweight metadata and scheduler work only. Source-locked historical results remain unchanged.

Benchmark scripts are code: test every active runner with a small fixture, then audit it against the current public API, package reference manual and GitHub Pages. The isolated candidate exports 31 functions; GitHub main still shows the old broad interface. The 42 older benchmark scripts calling newly internal stages must be classified as historical evidence or migrated active callers before a new release. Rebuild vignettes, manual and site from the same reviewed commit.

## 3 Run independent benchmark lanes now

Do not impose a platform-wide serial wait. Run CPU and Metal cases as soon as their own candidate and inputs pass checks, even when CUDA quality or multi-GPU implementation is unfinished. Record a failing quality case rather than suppressing its timing; it cannot support a performance claim until resolved. Run resident CPU cases on HPC independently of the L40S pilot. Mac timing jobs must not overlap on the same hardware. Hugging Face is the lower-cost multi-GPU development lane; use source-locked bounded jobs within Stefano's approved additional US$3. Chiamaka remains available for CUDA file-backed development only when Bora's workload is absent and the idle gate passes.

The Mac COIL20, USPS, MNIST, Fashion-MNIST, MetRef and Tabula Muris unified-API CPU/Metal pilots completed. MNIST and Fashion-MNIST each used all 70,000 rows, and Tabula Muris used all 100,102 rows; these remain single-seed development evidence, not formal JSS results. A separate Tabula Muris 3D CPU/Metal pilot completed all six cases, with an explicit three-coordinate output check. New source-locked COIL20 one-case runners added three-seed UMAP CPU/Metal measurements, 3D t-SNE/UMAP CPU/Metal checks, and four-core CPU checks across the five public methods; these are still development cases. The separate fixed-graph Fashion quality check still finds a Metal UMAP gap despite the full-dataset pilot's similar trustworthiness. UCT resident CPU COIL20 and USPS five-method cases completed under the older b825116 image; keep their source identity. L40S pilot 1570379 failed before scientific child start on GPU index-to-UUID mapping. Allocation-only diagnostic 1579109 confirmed remapping; corrected resident two-L40S pilot 1587409 completed with compute-node image verification and owned-context cleanup. It used only 160 synthetic rows, so real-data quality and speed remain open. Hugging Face four-L4 clustering job 6aeca76d0e0338d1bb808d2e completed a 12-vertex exact-label/modularity and context-cleanup test on all four GPUs; physical over-VRAM and performance remain open. An isolated file-backed CUDA clustering worker accepts five-device routing with bounded global shutdown waits; it has CPU-side tests but no five-device qualification.

Expand the eleven comparison datasets, CPU core grid, 1/2/3 L40S device grid, landmark fractions, 3D outputs and Mac file-backed comparisons with source-locked, independently admissible cases. Each configuration keeps its status even when unsupported. Deep1B 10M stress runs on Mac/HPC under their machine policies, and Mac file-backed scaling proceeds through the 100M subset as feasible. Generate manuscript figures and tables only from a frozen, audited result cohort.

## 4 Separate one-billion-row milestone

A full one-billion-row Deep1B fit without landmarks is a separate scale milestone, not a gate on the next release. Develop dynamic GPU-count support and partition graph, layout and optimizer state without a single-device capacity bottleneck. Audit 64-bit offsets and edge counts. Fit stage-specific time, RAM, per-GPU VRAM and storage models to observed 1M/10M/100M cases; validate against a held-out size before estimating the 1B hardware and runtime with uncertainty. A completed 1B result requires an actual fully audited fit on a permitted machine; otherwise label it a projection.
