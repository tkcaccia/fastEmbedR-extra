Turing's 1M-row unsharded index with M=32 and efConstruction=200 reached
holdout mean recall 0.994 (lower 95% bound 0.993) at efSearch=960. The
same built index at efSearch=150 returned 0.968 (lower bound 0.964).
Its measured 2,048-query pass took 3.66 versus 0.58 seconds on the same
node. That is a real recall/latency trade-off, not a full-call speed ratio.

For Turing with 50k-row shards, the existing M=32/efConstruction=200/
efSearch=150 preset already reached 0.996 holdout recall. On Deep with
50k-row shards, M=24/efConstruction=160/efSearch=45 reached 0.996 versus
1.000 for the preset, while its measured build and 2,048-query pass were
33.8 and 0.80 seconds versus 52.6 and 2.40 seconds on the same node.
This is a promising speed candidate, not a new default.

The new recall-constrained speed screen nominates one setting per group for
a declared all-row query workload. Four of 24 nominees miss the separate
holdout lower-bound check, all on Turing at 1M rows: 20k shards/k15,
50k shards/k30, and unsharded/k15 or k30. The original campaign audit
reported no task failures, but did not count these recall misses. The
revised audit does. Cross-node projected times are provisional, and worker
peak RSS is not a full fastEmbedR-call memory measurement.

Deep and Turing have nearly the same feature count but different neighbor
structure. On the 20k pilots, the median exact distance ratio d30/d1 was
1.218 for Deep versus 1.138 for Turing; the most frequent sampled top-30
neighbor appeared 27 versus 112 times. Those observations suggest harder
search geometry on Turing, but do not establish a causal explanation.

## Focused follow-up

### Image gate

The screened image has faissR 0.99.50 and fastEmbedR 0.1; it cannot
test the new workload-aware faissR tuner. After faissR 0.99.52 and its C API
are frozen and validated, build a candidate SIF from source-identified
faissR and fastEmbedR archives using the existing Chiamaka definition as a
base. Confirm both package versions, DLL hashes, C-callable resolution,
CPU HNSW build/repeated search, and the tuner holdout-failure path in the
candidate image. Only after those checks pass should the candidate replace
the stable `fastembedr_cuda.sif` name. Verify its SHA-256 again on the HPC
inside a compute-node preflight. Do not submit the 5M run against the old
image. Retain the original image hash in campaign provenance.

### Experiment order

1. Freeze the new faissR workload-aware tuner and rebuild a source-locked
   test image. The screened image still has faissR 0.99.50. Keep the fixed
   shape-policy arm separate from adaptive tuning.
2. Start with a fresh 5,000,000-row view of each billion-row file, beginning
   after the 1M-row development prefix. Use file-backed input, 50k-row
   shards, k=30, and the existing faissR HNSW route. Compare the current
   preset with a small prespecified candidate set, not a new exhaustive
   sweep. Compute exact truth for at least 8,192 seeded query rows, split
   evenly into tuning and untouched holdout. Record source hashes, build
   and query times, peak RSS, and per-query recall; fail explicitly if the
   fit cannot respect the memory budget. Do not load the 1B file into RAM.
3. On one CPU node, repeat build and 8,192-query timing for a small,
   prespecified finalist set: Deep 50k preset versus M24/160/45; Turing
   50k preset; Turing 20k M16/200/120; and Turing unsharded M32/200/960.
   Use at least three runs and report median plus dispersion. Follow with
   an all-row KNN call only for a holdout-confirmed finalist whose projected
   cost fits the job limit. Do not rank by the original cross-node seconds.
4. Report mean and lower-bound recall, tenth-percentile and minimum
   per-query recall, and boundary ties. Use fresh query seeds and repeat
   the frozen selection on an unseen prefix; the 5M-row stage must not use
   the same first million rows used to design the candidate grid.
5. Only if Turing's unsharded route remains slower than sharding at the
   target recall, test a bounded higher-M/higher-efConstruction grid that
   might permit a lower efSearch. Do not repeat the full 52-case sweep.
6. Compare final fastEmbedR KNN calls, including calibration, disk reads,
   all-row queries, peak process RSS, and index reuse. Then check whether
   the same settings preserve UMAP/t-SNE quality. Promote no default until
   this end-to-end and independent-prefix evidence agrees.

### First larger-sample gate

The first HPC run after the image preflight is **5 million rows per dataset**,
not another 20k or 1M pilot and not a claim about 1B-row performance. Use
rows 1,000,001--6,000,000 of each completed `.fbin` as a file-backed view;
do not copy the vectors. Start with CPU HNSW, 50k-row reference shards,
four CPU workers, and k=30. Keep the current faissR shape preset as the
control. Test only the predeclared Deep M24/efConstruction160/efSearch45
candidate and Turing M32/200/150 preset; a calibration-selected setting
is an additional arm only when its explicit build settings can be passed
through the fastEmbedR bridge and recorded in the output.

Compute streamed exact neighbors on 8,192 seeded query rows, with 4,096
for selection and 4,096 untouched holdout rows. Run exact truth and the
bounded sampled-query search before any all-row graph construction. Require
the lower 95% bound on mean holdout recall to reach 0.99, and report the
mean, tenth percentile, minimum, and boundary-tie count. A failed recall
gate is a measured result, not a successful calibration. Repeat finalist
build/query measurements three times on the same CPU node; report median
and dispersion, total calibration time, build time, search time, and peak
process RSS. Keep a strict file-backed memory budget and save only exact
IDs/distances, per-query recall, metrics, and source identity.

Launch a complete 5M-row KNN graph only for a holdout-confirmed finalist
whose sampled-query projection fits the declared job walltime and free-disk
budget. The full call must report its own elapsed time and peak RSS; the
projection is not a substitute. Checkpoint/resume is tested separately
from the timing run. If this stage passes, use the resulting graph for
one UMAP and one t-SNE fit and compare quality on fixed rows. Run Deep and
Turing independently so one slow dataset cannot block evidence from the
other. No GPU jobs are needed for this CPU HNSW calibration stage.
